# 目的を保持し、観測に基づいて計画を変える共通ループ

状態: S1を実装しCPU検査で検証。稼働中のGUIとは独立したGenesis実行は未検証。
S2以降、モデル選定、性能改善は未実装・未検証。
基準: `fix/instruction-contract @ b52629b`。本計画は PR #18 の投擲変更とは別トピック。

## 目的

モデルが操作列を生成して終わるのではなく、固定した要求に対して、観測、実行前検査、原因仮説、
検証、手順変更を繰り返す。達成不可能・情報不足・能力不足を、成功や別作業へ変換しない。
汎用性は「どんな物理動作でもできる」ことではなく、同じ契約と制御ループを異なる操作に適用できること。

## 実装を読んで分かった出発点

- `agent/task_agent.py::TaskAgent.run` は既に observe/prepare/execute/recover を持つ。
  新しいエージェントを横に追加せず、この所有者を改善する。
- `replan` 分岐は `original = replanned` として、最終判定の基準まで更新する。
  未指定の腕の選択変更と、明示要求の変更を独立して表現できていない。
- 復旧をモデルに選ばせる呼び出しには category/detail/prefix 等しか渡さず、
  `failed.evidence` は別の再計画呼び出しで渡す。診断と再計画で証拠の粒度が異なる。
- 再計画を許す条件に detail 内の `design` という文字列や `levers` の有無を使っている。
  数値がない失敗、未観測、能力不足、経路衝突の区別が型として揃っていない。
- `planning/goal_search.py` と `execution` の goal-program 経路にも局所探索と再観測がある。
  外側の復旧で内側の失敗履歴を消さないよう既存コードが個別に注意している。
- `verification/goal_verification.py::verify_task_goal` は state と event を同じ入口で検証する。
  throw/pour は results にある軌跡・流量履歴を使うが、TaskAgent の最終再検査は `steps=[]`, `results=[]`。
  GUI記録では throw の自由飛行上昇が約43.7 mmで成功した後、空の履歴で `NO_UPWARD_FREE_FLIGHT` になった。
  現在状態だけでは過去の出来事は再検証できない。
- `TaskProgram` は actions または goals の一方。既存 `TaskGoal` は holding/placement/relative_placement。
  throw/pour/順序/途中の保持を、単なる最終姿勢の goals に無理に変換しない。
- `b52629b` は解決できない参照、拒否済みfallback、保持条件の脱落を防ぐ境界。
  任意の自然言語の理解や、保持した支持物上への配置能力を追加したものではない。

## 不変条件（モデルを替えても変わらない）

1. **契約と手順を別の値にする。** 手順は更新できるが、契約は再計画で上書きしない。
2. **固定するもの:** 対象ID、明示した腕、数量、関係の主語/支持物、禁止、必要な順序、保持すべき区間。
   **未指定のもの:** 利用可能な腕や経路などの選択肢として保持し、最初の計画の既定値で固定しない。
3. 言語モデルの抽出も仮説。原文span、参照先、解決/未解決を記録する。意味の脱落・曖昧さは
   再質問/修正または動作前の確認要求にする。自己申告の confidence だけで採用しない。
4. 不足する単位・距離・丸め・許容値を新設の既定値で埋めない。既存の物理検査の値を再利用する。
5. 証拠は task/attempt/action/scene epoch/観測時刻に結び付く。別の初期化前の証拠を流用しない。
6. 仮説と観測事実を分離する。LLMは接触・成功・到達可能性を観測したことにできない。
7. 未実装と、現在の条件で不成立と、未知を区別する。UNKNOWN を実行可に丸めない。
8. 不可逆な達成済み操作を、最終判定や復旧のために自動で再実行しない。
9. 同じ状態・同じ操作条件・同じ証拠なら再試行しない。関連する変化の根拠があって初めて再開する。
10. Genesisの単一所有権、collision/effort制約、物理把持、停止要求を維持する。live pose を書き換えない。

## 所有者とデータの境界

```text
原文 + 現在の観測
  -> 解釈案 -> 意味/参照検査 -> 凍結した TaskContract
                                   |
観測 + EvidenceLedger + Contract -> 候補/仮説
  -> 契約保存検査 -> 前提検査/非破壊query -> 採否
  -> 既存スキルを実行 -> 実測記録 -> 契約で検証
       ^                              |
       +--- 有効な変更がある場合だけ再計画 ---+
```

配置案（詳細は実装時に既存型へ統合し、同じ概念を二重所有しない）:

| 概念 | 所有先 | 責務 |
|---|---|---|
| TaskContract | planning の契約型 | 原文根拠、固定束縛、自由な選択肢、state/event/temporal要求、保護条件 |
| Contract evaluator | verification | 現在状態と型付きイベント証拠から SATISFIED/UNSATISFIED/UNKNOWN を判定 |
| EvidenceLedger | execution | 実行と検査のreceipt。モデルの説明文とは別に保持 |
| FailureObservation | execution/verification | 実測値、試行条件、violated precondition、証拠ID、unknown |
| RecoveryProposal | planning | 原因仮説、根拠ID、変更点、確認方法、期待する判定差、棄却条件 |
| Query catalog | 既存のplanning/simulation境界 | IK/衝突/能力等の読み取り。未対応queryは UNKNOWN/UNSUPPORTED |
| Recovery loop | TaskAgent | budget、再計画採否、進捗、停止。goal-searchは候補生成に限定 |

新しい能力登録は、入力型・前提・効果・query・実測verifierを揃える。
特定の色・腕・タスク名を recovery loop に追加して能力を増やさない。
既存 task/action IDs と契約上の obligation IDs は別物。再計画でaction indexが変わっても、
完了済みobligationの証拠対応を失わない。

## 実装順（5スライス）

### S1: 目的契約と state/event の検証を分離する

- 原文からの解釈案と採用された契約を区別。手順と関係なく契約IDと要求IDを発行し、採用後に凍結する。
- 既存 TaskGoal/TaskAction/check を活用し、最終状態、出来事、順序付き操作、during条件を分類する。
- 指定腕と未指定腕を区別。意味を解決できない場合は動作前に止める。
- 最終状態は現在の物理状態、出来事は対応するtrajectory/流量receiptで検証する。
  停止・初期化・再計画・homingの後も証拠のscopeを明示して扱う。
- during条件を測る既存観測がなければ、未検証として停止。暗黙に最終状態へ弱めない。
- `original = replanned` に依存する判定基準を撤去。新旧ループを同時に正規経路として残さない。

**合格:** 模型の候補が手/対象/量/支持物を変えると実行前に拒否される。未指定腕の変更は可能。
成功済みthrowは最後の再検査で失敗せず、軌跡なし/別epochのreceiptでは成功しない。
途中の保持を解除した試行は、最後に掴み直してもduring条件達成にならない。

**レビュー面:** 物理を起動しない契約差分・receipt検査CLI。元の要求と候補の差、欠けた証拠をJSONで表示。

S1の入口は `scripts/check_task_contract.py`。運用上の契約と検証範囲は `docs/TASK_AGENT.md` の
「目的契約と実行証拠」に集約する。最初の型付き解釈の正しさを独立に証明するものではなく、
duringの検出も既存言語表現の範囲であり、連続観測がない要求はUNKNOWNで止める。
操作列の置き換えは明示要求を保つ保守的な検査に限定し、未宣言の退避操作追加を承認する仕組みはS3に残す。

### S2: 証拠・失敗・操作前提を揃える

- 既存スキル結果を同じ FailureObservation/Evidence receipt 形式へ正規化する。
- skill結果だけでなく実行前のIK/衝突拒否も記録。生の測定値と由来を残し、欠損値を0にしない。
- 原因の分類は REACHABILITY / PATH_COLLISION / TRACKING / HOLD / UNSUPPORTED / UNKNOWN 等の共通分類。
  到達不可の測定がない場合、単なるIK失敗から「腕が短い」と断定しない。
- 関連状態のfingerprintは操作の前提から作る。時刻や説明文の変化だけでは新状態と扱わない。
- 既存queryから始める。途中の衝突位置を返せないqueryに、架空のリンク情報を足さない。

**合格:** 状態変更なしの同一失敗を識別できる。座標/保持/障害物の関連変化は識別できる。
失敗した操作の測定値が、診断・再計画・GUIで同じ証拠IDを指す。

**レビュー面:** 同一観測receiptのリプレイ。候補は作るがlive sceneは動かさない。

### S3: 仮説を検査し、契約を守って再計画する

- モデルは自由な説明だけでなく、根拠IDと検証案を持つ RecoveryProposal を返す。
- ループが道具の存在、入力範囲、停止可否、契約保存、予算を検査する。
- IK/衝突/能力等の非破壊queryを優先。非破壊検査だけで分からないときは UNKNOWN のまま扱う。
- 動作を伴う探索は通常の安全な実行として記録し、こっそりprobeしない。契約の禁止条件は緩めない。
- queryの結果と予測が違えば仮説を棄却。関連変化がない同一候補は二重実行しない。
- 内外の探索は同じbudgetと失敗履歴を共有。TaskAgentからgoal-searchを呼び直しても記憶を失わない。
- 再計画成功は「候補が採用された」であり、物理成功は契約verifierだけが判断する。

**合格:** 干渉が原因のfixtureでは退避候補を検査後に採用。可動域制限のfixtureでは同じ退避を繰り返さない。
モデルが架空の根拠・新しい道具・目的変更を返しても実行されない。停止要求で後続候補を実行しない。

**レビュー面:** 既存のTaskAgent fake executor + 実query adapterで、状態遷移と採否理由を時系列表示。

### S4: GUIで何を根拠に変更したかを見せる

- 既存 `agent_trace` と「状況判断と復旧」パネルを拡張し、別の状態所有者を作らない。
- 固定目的 / 観測事実 / 原因仮説 / 検査結果 / 変更した条件 / 未達条件 / 残り予算を区別する。
- 「モデルが呼ばれた」「回答を採用した」「fallbackを採用した」を別表示にする。
- 原文・モデル要求/応答・query receiptはローカル保存し、秘密や無関係な会話を混ぜない。
- 画面の表示がログと同じ証拠IDを指すことをブラウザで検証する。

**合格:** 失敗原因が未知なら画面も未知。失敗を成功の文章で覆わず、停止後の遅延応答で再実行しない。
既存表示に影響する変更は screenshot-critique、比較対象がある場合は compare-screenshots を通す。

### S5: 未見ケースで評価し、必要ならモデルを選び直す

- deterministic fixture群を先に固定し、開発用とheld-outを分ける。失敗例だけを集めた評価にしない。
- 同じ初期状態/契約/道具/予算でモデルを比較。速度、採用率、契約違反、false success、回復率、
  無駄な再試行、正しい停止、解けるのに拒否した数を別々に報告する。
- LFMのLLM/VLM/判断モデルは候補。モデルID/版/重み/ライセンス/実行経路/必要メモリを確認してから採用。
  具体的なモデルを未検証のまま計画の前提にしない。
- smallモデルの失敗が証拠解釈にあるか、意味抽出にあるか、道具不足かを分離する。
  大きいモデルへのルーティングは差を測れた場合だけ導入する。
- VLMは画像証拠が必要な場合だけ。現行のGenesis真値ベースの認識を「VLMによる認識」と称さない。
  neuron介入や追加学習は本計画に含めず、固定評価で残ったモデル由来の欠点が根拠になった場合の次段階。

**合格:** 既知の正常ケースを維持し、異なるfixtureの到達/干渉/保持/イベント/意味欠落を同じループで扱う。
false success/目的変更/未対応操作の強行は1件でもgate失敗。全拒否は解決可能ケースのgateで失敗する。
確率的モデルの回復率等は複数試行で報告し、合格率の閾値はbaseline後に承認する。

## 検証行列

| 変数 | 必須の両側 |
|---|---|
| 指示の自由度 | 明示した手は固定 / 未指定の手は選択可能 |
| 意味 | 同義の言い換え / 一語だけ変えた別条件 |
| 順序 | 中間配置の変更可 / 明示した順序とduring条件は不可 |
| 原因 | 経路干渉 / 可動域不足 / tracking不足 / 未観測 / 未実装 |
| 証拠 | 現在のstate / 過去のevent / stale receipt / 別epoch |
| 達成 | 回復で達成可能 / 正しく停止すべき / 初回で成功 |
| 再試行 | 関連状態変化あり / 無関係な時刻変化のみ |
| 汎用性 | 色・左右・対象ID・関係・配置・言語表現を変更 |

typed fixtureで対象IDを変えた検証と、その名前を自然言語から認識できるかの検証は分ける。
既存物理スキルで検証できる物体から始め、URDF取込機体の未校正ピンチを成功条件に使わない。
新しいguardは旧実装または故障注入でredを確認してからgreenを記録する。

## 予算と実行経路

- まずS1/S2のCPU-only fixtureで反復。既存TaskAgentの最大attempt=4を増やさない。
- query数・モデル修正回数・wall timeの共通上限はS2の測定後に決定し、S3実装前に凍結する。
  個別の内部ループで予算をリセットしない。
- resetは通常の問題解決手段にしない。既存の観測された回収不能状態とreset予算以上に許可を広げない。
  resetを許す場合はepochを変え、出来事の証拠も新しいepochで必要か契約に従い判定する。
- Genesis/GPU検証はfresh resource gate + MemoryMax、GUIとの単一所有権を守る。
- 外部公開・モデルdownload・大きいcomputeはそれぞれ承認/資源規則に従う。
- APIの二重実装や新旧契約の恒久互換層は作らない。保存済み旧実行記録は診断資料として扱い、
  新しい契約の達成証拠として自動昇格しない。外部互換/永続データmigration要件があれば実装前に確認する。
