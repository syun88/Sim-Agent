# 実測状態から最終目標へ手順を探索する

## 解決する問題

従来の経路は、自然文を順序付きの操作へ翻訳し、それぞれを決まったスキル列へ展開していた。
そのため「左手に青、右手に赤を持たせたい」という最終状態でも、既に両手が塞がっていると、
直接の受け渡しや追加の把持を拒否して終了していた。必要な一時置きは、利用者が手順として指定する必要があった。

追加した経路では、最終目標と動かしてはいけない物体を先に確定し、現在の物体・手・支持関係から準備動作を探索する。
動作後にはGenesisを再観測し、最初の予測をそのまま次の実測状態として扱わない。
順序や使用する手を明示した既存の指示は、従来の順序付き経路でその指定を保つ。

## 公開研究との関係

2026-10-23時点で、次の一次資料を確認した。

- [VeriGraph, ICRA 2026](https://verigraph-agent.github.io/): 状態グラフを計画と検証で共有する。本実装でも支持関係と手の占有を明示するが、画像からのグラフ生成は実装していない。
- [Verifier-Mediated Multi-LLM Coordination, 2026-10-08](https://arxiv.org/html/2610.12761v1): 幾何的な不成立を構造化したフィードバックとして計画へ戻す。本実装の失敗遷移の除外に関連する。ただし、この論文の評価領域はCARLAとCrazyflieの協調移動で、本プロジェクトの把持との優劣を比較したものではない。
- [FlowPlan, 2025](https://arxiv.org/html/2503.02698v1): 言語の推論、記号的な計画、論理検証を分ける。本実装では、小型モデルに準備動作をすべて推論させる代わりに、型付き目標から有界探索を行う。
- [ReKep, 2024](https://arxiv.org/abs/2409.01652): 関係を制約として表し、動作へ落とす方法。本実装は既知のキューブと既存コントローラーが対象で、ReKepのキーポイント生成や汎用の接触動作生成を再現するものではない。
- [UniPred, T-RO 2026](https://unipred.github.io/): 述語の獲得と実行後の再グラウンディングを扱う。本プロジェクトではFT・デモ学習を追加せず、Genesisの実測値から計算する述語を使う。

これは既存研究にある要素を、このシミュレーションの観測と物理検証に合わせて統合した実装である。
世界の全手法より優れるという主張や、論文の評価値との直接比較はしていない。
比較対象は同じ世界状態での従来コンパイラーであり、探索の成立と物理実行の成功も別に記録する。

## 入出力

未知の文は、まず `InstructionMeaning` で意味を抽出する。この文脈には動作レシピや関節の数値を入れず、
最終状態を求める指示、順序付きの操作、未対応を区別する。最終状態なら目標条件を検証して探索へ渡す。
順序付きなら次の動作解釈を使う。意味抽出と動作解釈を合わせた問い合わせは最大3回。

動作解釈のモデルは `ActionProposal` を返す。`mode` は `actions`・`error`、内容は1つの動作 `items` 配列に限定する。
小型Ollamaモデルが別々の `actions` と `goals` を同時に埋める問題を避けるため、
モデル用の出力形式とコンパイラー用の `TaskProgram` を分離した。
混在した項目、未知のフィールド、型の異なる項目は検証で拒否する。

要求された保持者を現在の保持者と混同する問題にも対応する。`planning/goal_language.py` が、
文に明示された物体と手の組、観測した両手の中身を交換する要求を独立した制約として抽出する。
明示的な最終保持者の補正は、モデル回答との違いと元の文を `semantic_binding_repairs` へ残す。
手順中の一時的な保持者を最終目標に変換しない。これは全文を理解したふりをする文法ではなく、
意味解釈と併用する限定された照合であり、未知の言い換えを常に証明できるわけではない。

コンパイラーへは、従来の `actions`、または次の `goals` のどちらかを渡す。

```json
{
  "goals": [
    {"type": "holding", "object": "blue_cube", "arm": "left"},
    {"type": "holding", "object": "red_cube", "arm": "right"}
  ],
  "keep_in_place": []
}
```

最終目標は保持 `holding`、机領域への配置 `placement`、物体を基準にした配置 `relative_placement` の3種類。
1つの手に2つのIDを保持させる要求、同じ物体について矛盾する目標、未知の物体・行き先を拒否する。
目標の主語ではない物体と `keep_in_place` の物体は、保護する位置をタスク開始時に固定する。
モデルが勝手に「赤もどかせばよい」と追加できる構成ではない。

## 探索する状態と操作

`planning/goal_search.py` は、物体ごとに次の状態を持つ。

- 初期の机上位置、既知の机領域、別の物体との配置関係。
- 左右いずれかの手による保持。机上のピンチは空中保持と区別し、持ち上げを残す。
- 支持している物体と、その上を空ける必要がある関係。
- 空いた腕の受け渡し準備。単に指が空いていることと、退避を終えたことを区別する。

操作は既存の `pick`・`handover`・`place`・`home` の効果として列挙する。
受け手が塞がった受け渡し、上に物体が載ったままの下の物体の取得、保護対象の移動を候補から除く。
机の領域を一時置きに使い、物体の衝突境界から置き場所の重なりを調べる。
配置時に確認された担当腕や物体の左右位置を探索コストへ使うが、それを現在のIK・経路の証明とはしない。

探索は最大4,000状態・24操作、最終目標は最大12件で打ち切る。
使えるスキルがない場合、解がない場合、予算を使い切った場合を動かす前に返す。
ここでの合格は記号的な前提条件の検証であり、連続軌道や把持の物理的な成立は実行側でさらに検査する。

## 実行と再計画

`execution/goal_executor.py` は、探索した手順の最初の意味的操作だけを共通の `TaskExecutor` へ渡す。
取得後に受け渡す予定がある場合のパッド位置など、残りの手順を見て計算した引数も引き継ぐ。
操作後に再観測し、残った目標を再探索する。達成済みの目標から先頭の取得動作を録画再生し直すことはない。

生成した `home` の準備には `park_empty_arm` を使う。モデルの初期関節から専用FKで退避先を求め、
物体の寸法に応じて上昇し、高い位置で移動・姿勢変更してから降下する。
机上の物体への接触・2mmを超える押し出しと、他方の保持の喪失を監視する。
従来の単一関節補間によるホーム移動は、一時置きしたキューブを横切る失敗があったため、目標経路の準備には使用しない。
退避完了の記録は実測した手先姿勢に結び付け、手先がずれたり次の動作に使われたりしたら解除する。

机上の接触のない失敗した取得だけは、最大2回、失敗した物体状態と手の遷移を除外して別案を探索できる。
空の手を退避させただけで同じ失敗遷移を再許可しない。物体を持ったままの失敗や途中の受け渡しは停止する。
失敗した試行も `verification.execution_attempts` とスキル結果へ残し、成功した試行だけに履歴を書き換えない。
シーンの初期化、物体の姿勢の書き換え、LLMによる成功宣言は回復手段に使わない。

最終的に目標が満たされたと観測したら `observe_scene` を実行し、既存のGenesis事後条件検証をもう一度使う。
両指の物理把持、持ち上がった位置、支持接触、解放、静止、保護した物体の変位を確認する。
中間操作のフレーム条件はタスク全体に合わせる。例えば、最終目標に含まれる別のキューブが保持されたまま位置を変えることと、
動かしてはいけない土台が押し出されることを同じ条件では判定しない。保持と保護位置の検証自体は省略しない。

## 検証

```sh
uv run pytest -q backend/tests/test_goal_search.py
uv run python scripts/verify_goal_planning.py --json outputs/goal-planning-verified.json
uv run python scripts/verify_goal_language.py --json outputs/goal-language-verified.json
uv run python scripts/verify_goal_planning.py --case swap --provider local --json outputs/goal-planning-local.json
```

2026-10-23の公式OpenArmのGenesis試験では、次の2ケースが成功した。

- 左で赤・右で青を実際に取得した後、「両手のキューブを入れ替えて」。直接受け渡す従来計画は受け手占有で拒否。
  新しい計画は青を中央へ一時置き、右腕を退避、赤を左から右へ渡し、青を左で取得した。実行約3.60秒、再試行0。
  最後に青を左・赤を右が両指で保持し、机より上にあることをGenesisから確認した。初期構築と事前の2つの取得はこの時間に含めない。
- 赤を保護した青の積み重ね。実行約4.19秒、再試行0。中心ずれ約0.372mm、支持面の重なり約99.37%、
  実際の支持接触・解放・静止あり、赤の移動約0.040mm。

記録はローカルの `outputs/goal-planning-verified.json`。これらは通常初期配置の2ケースで、
広いランダム配置の成功率、任意のURDFの成功、すべての自由文の意味理解を証明するものではない。
初期試作で失敗した退避や、動作と目標が混在したモデル回答も別の診断記録に残した。

通常のランチャーをヘッドレスで起動し、Webと同じ `POST /api/tasks` から両手の取得と続く持ち替えを送った経路も成功した。
それぞれ実行約1.20秒・3.76秒、再試行0、観測して残りを探索するループは3回・5回。
`outputs/native_goal_planning_validation.json` に記録した。ブラウザーのボタン操作や可視ウィンドウの検証は含まない。

`verify_goal_language.py` では、実Ollama `qwen3-vl:4b` が日英の保持者変更、保護対象を含む積み重ね、
元の順序付き指示の4例を解釈し、型だけでなく実際の物体・手・参照物・順序を確認した。
同時集合把持の追加1例は、意味を単一把持へ縮めず能力チェックで拒否した。
`outputs/goal-language-current.json` が5ケースの記録で、3つの最終状態の解釈は約1.93〜2.31秒。
この記録は凍結した観測状態に対する言語・計画の検証であり、別の物理実行として数えていない。
全体の回帰は `uv run pytest -q` で185件成功（22.82秒）。

## 残る境界

この探索は、既存のコントローラーにない物理動作を発明しない。積んだ2個を1つの手で同時に把持する集合表現、
擦る・拭くなどの接触制御、自由な動作コードの生成、VLMによる未登録物体の認識は引き続き未実装。
登録済みの物体に対するGenesisの正解状態を観測する前提も変えていない。
FT・VLA・学習したworld modelを追加せずに、手順の探索と再観測を強化した段階である。
